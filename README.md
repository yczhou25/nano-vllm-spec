# nano-vllm-spec

[![Tests](https://github.com/yczhou25/nano-vllm-spec/actions/workflows/tests.yml/badge.svg)](https://github.com/yczhou25/nano-vllm-spec/actions/workflows/tests.yml) [![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

[nano-vllm](https://github.com/GeeeekExplorer/nano-vllm) (a ~1,200-line vLLM written from scratch by Xingkai Yu) extended with **async scheduling** and **speculative decoding**, plus a test suite that checks every KV-cache write and read.

在 nano-vllm 的基础上加了**异步调度**和**投机解码**（n-gram 草稿和小模型草稿，两者都可以和异步调度组合），并补了一套在 CPU 上就能跑的测试：用假模型驱动真实的调度器、块管理器和输入准备，逐一检查每次 KV cache 的写和读。

## What's new

| Feature | Where | Notes |
|---|---|---|
| Async scheduling | `nanovllm/engine/llm_engine.py`, `scheduler.py` | The CPU schedules step *n+1* and prepares its inputs while the GPU runs step *n*; sampled tokens are filled in one step late. `LLM(..., async_scheduling=True)` |
| N-gram speculative decoding | `nanovllm/engine/ngram.py`, `model_runner.py` | Prompt-lookup drafts: propose `k` tokens from earlier text, verify them in one forward pass. `LLM(..., num_speculative_tokens=k)` |
| Draft-model speculative decoding | `nanovllm/engine/model_runner.py`, `block_manager.py` | A smaller model of the same family drafts; it keeps its own KV cache and block tables. `LLM(..., speculative_model=PATH)`; combines with `async_scheduling` |
| Rejection sampling | `nanovllm/layers/sampler.py` | Accept/reject drafts so outputs follow the target model's distribution; greedy with `temperature=0` With a draft model (`speculative_sampled_drafts`, the default) each draft is sampled from the draft's own distribution at the sequence's temperature (Gumbel-max on the logits, compiled) and accepted with `min(1, p/q)`, the rejected position resampled from `max(0, p-q)`; q is computed inside the compiled rejection sampler from the draft's bf16 logits, so nothing but those logits is stored: exact speculative sampling, with the acceptance rate `sum(min(p, q))` instead of `p(argmax)` at temperature > 0 (A40, Qwen3-8B + 0.6B, chat at T=0.8: acceptance 0.39 to 0.42, +5-7% throughput at batch 8-32; the greedy path is unchanged) |
| Adaptive speculation | `nanovllm/engine/scheduler.py`, `model_runner.py` | The scheduler picks each decode step's `k`: `LLM(..., speculative_disable_by_batch_size=n)` drops drafts while more than `n` sequences are running, where the GPU is busy anyway; `speculative_min_acceptance=r` tracks the acceptance rate of every draft position over its last 64 samples (at least 8 steps) and proposes only the leading positions that reach `r` (down to none), with one full-`k` probe step every 16 steps to let positions back in. Steps without drafts skip the draft model; its KV cache lags behind and the next step with drafts catches it up in one forward pass |
| Per-sequence k (ragged drafts) | `nanovllm/engine/scheduler.py`, `model_runner.py`, `layers/sampler.py` | `LLM(..., speculative_min_acceptance=r, speculative_per_sequence=True)` keeps the acceptance rates per sequence, so each sequence proposes its own number of drafts (probes stay one uniform step for the batch). A batch whose sequences differ runs either padded to the most drafts with dummy rows in front of each sequence, through the fixed-width kernel and the CUDA graphs (`speculative_ragged="pad"`, the default), or through the varlen attention kernel over the block tables, eagerly, one row per token (`"varlen"`); a layout tensor says which rows are whose and the rejection sampler masks the positions a sequence does not have. Batches with one `k` for everyone are unchanged |
| Tensor-parallel fixes | `sequence.py`, `model_runner.py` | Decode slot mapping used the model's block size instead of the runner's; prefill sent unscheduled tokens to TP workers (both found by auditing the code) |
| Test suite + CI | `tests/`, `.github/workflows/tests.yml` | Runs on CPU with stubs for flash-attn and triton; GPU tests compare greedy outputs with `transformers` |

Design notes: [async scheduling](docs/async-scheduling-design.md), [speculative decoding](docs/spec-decode-design.md). Write-up (Chinese): [在 1,400 行的推理引擎里实现异步调度和投机解码](docs/blog/spec-decode-in-1400-lines.md).

## Quick start

```bash
pip install git+https://github.com/yczhou25/nano-vllm-spec.git
huggingface-cli download --resume-download Qwen/Qwen3-8B --local-dir ~/huggingface/Qwen3-8B/
huggingface-cli download --resume-download Qwen/Qwen3-0.6B --local-dir ~/huggingface/Qwen3-0.6B/
```

```python
from nanovllm import LLM, SamplingParams

llm = LLM("~/huggingface/Qwen3-8B/",
          async_scheduling=True,
          num_speculative_tokens=4,
          speculative_model="~/huggingface/Qwen3-0.6B/")
outputs = llm.generate(["Hello, nano-vllm."], SamplingParams(temperature=0.6, max_tokens=256))
print(outputs[0]["text"])
```

Drop `speculative_model` to draft with n-grams instead (n-gram drafts do not combine with `async_scheduling`). Add `speculative_disable_by_batch_size=8` to speculate only for small batches, or `speculative_min_acceptance=0.2` to let the measured acceptance rate of each draft position pick `k` per step, from `num_speculative_tokens` down to none (n-gram drafts on chat, for example, get switched off); add `speculative_per_sequence=True` to pick it per sequence instead of per batch, for batches that mix workloads. Without any of these options the engine behaves like upstream nano-vllm.

## Tests

```bash
pip install pytest
pytest                                                        # CPU: scheduler, block manager, input prep, sampler, n-gram, adaptive and per-sequence k, simulator
NANOVLLM_TEST_MODEL=~/huggingface/Qwen3-0.6B/ pytest -m gpu   # GPU: greedy outputs vs. transformers with teacher forcing
```

`tests/engine_sim.py` is a randomized simulator: a fake model (and fake draft model) records what the engine writes to and reads from the KV cache, across chunked prefill, prefix caching, preemption, async scheduling and both kinds of speculation. `NANOVLLM_SIM_CASES=500 pytest tests/test_engine_sim.py` runs more cases.

With the draft model the switch pays exactly where draft positions get rejected, and costs nothing elsewhere. On chat at batch 32 it turns fixed k=4 from 1.04x into 1.19x and fixed k=6 from a loss (0.83x) into 1.08x, by settling on k=3 (380 of 453 steps) and k=2-3 (331 + 141 of 540 steps) respectively; on the mixed batch it turns 0.94x into 1.07x. Where every position clears the threshold (edit: positions accepted 0.72 to 0.92 of the time) it keeps k=K and matches fixed k within 1%. At batch 1 on chat it cuts K=6 to k=2 for most steps and the throughput does not move (63.4 against 63.6): a batch-1 step reads the weights once whatever its q, so the dropped positions were free, as the design note predicted. The 3.7x at batch 1 on edit that job 228429 reported was fixed k=6 from one job against adaptive k from another; measured together they are the same 3.2x.

N-gram drafts with the switch keep the edit speedup (1.54x) and are back at the baseline on chat at batch 1 (1.01x), but not at batch 8 (0.94x) or 32 (0.88x, up from 0.74x without the switch, and from 0.83x of baseline in job 228429 before the sampler and window fixes of 44129e2), nor on the mixed batch (0.88x). On chat at batch 32 the switch ran 928 of 1011 steps without drafts and probed with k=4 sixty times. Job 230846 (raw rows in `docs/benchmarks/qwen3-8b-a40-adaptive-k3.txt`) took that gap apart on its own node, where the baseline repeated three times within 0.3% (878.9 / 876.4 / 879.2, clocks pinned at 1740 MHz): the drafts-off path with the proposer present costs nothing (878.4 with drafts off at every step), and the switch costs 5.9% with a probe every 16 steps but still 5.2% with one every 64, so most of it is a fixed cost per run rather than a cost per probe. The probes themselves, at 1.4x a plain step, are about 1 point. The fixed part was `torch.compile`: it specializes sizes 0 and 1, and the samplers were only warmed up for a symbolic batch, so the first step with one sequence (every batch's tail) and one draft recompiled the rejection sampler inside the timed run, about 1.5 s per row (reproduced on CPU with the recompile log: six graphs in all, one of them compiled at the tail). Warming up batch size 1 did not remove it, and the recompile log of job 231468 (`docs/benchmarks/qwen3-8b-a40-adaptive-k4.txt`) showed why: `torch.compile` also guards on torch's default device, which `ModelRunner` had set to `cuda` while loading the model and warming up, and back to `cpu` for serving, so every compiled layer and both samplers were compiled again at the first real request and the startup warmup never counted (for a user that is the first request's latency; the bench's own warmup call hid it from the timer, but then the batch-1 warmup prompt 0/1-specialized the samplers and the timed run recompiled the rejection sampler twice). The warmup and the graph capture now run under the serving default device, with explicit device and dtype on every warmup tensor. Job 231709 (`docs/benchmarks/qwen3-8b-a40-adaptive-k5.txt`) confirmed that guard gone and the switch still at 0.94x (829.7 against 880.2 / 880.8, drafts off 881.0): the samplers were compiled again at the first real step on a `requires_grad` guard, because `run` and `run_async` were not under `torch.inference_mode` (only the model forward was), so the real logits carried autograd and the warmup's did not; after that the batch-1 warmup prompt 0/1-specialized them and a stride guard (the real drafts are a column slice of the step's input ids, the warmup's were contiguous) recompiled the rejection sampler twice more inside the timed run. The decode step and the sampler warmup now run under inference mode and the warmup drafts are a column slice like the real ones; on CPU the recompile log shows six graphs at warmup and none in a bench-like serving sequence. Job 232099 (`docs/benchmarks/qwen3-8b-a40-adaptive-k6.txt`, same node class as 231709) closed it: the switch is at 0.99x of the baseline on chat at batch 32 (871.8 against 881.2 / 881.6) and batch 8 (249.9 against 251.6), the drafts-off path is still free (881.4), and the recompile log has no sampler compile inside any timed run; every one falls in the startup warmup. What is left of the switch's cost is the probes. The draft model rows of the same job: fixed k=4 1.14x, K=4 with the switch 1.20x. So the 12 points of job 228654 were 7 points of node, 4 points of startup compilation leaking into the timed run, and 1 point of probes. On the mixed batch the switch oscillates (523 steps at k=0, 241 at k=4) because the batch-wide acceptance rates (0.31, 0.27, 0.25, 0.24) sit just above the 0.2 threshold: the edit half of the batch wants k=4 and the chat half wants 0, and one k per step cannot serve both. That is the design limit this switch has: a k per sequence (ragged drafts, as vLLM does) is the next phase, built below.

The GPU test suite (50 passed, 20 skipped across 14 engine modes) includes the new check that Qwen3-0.6B drafting for itself at T=1 accepts more than 90% of sampled drafts and 20-95% of argmax drafts. The code now keeps the draft logits in bf16 and reads q from them inside the compiled sampler, with the drafts drawn by Gumbel-max on the logits (job 245130 measured the first version of this at the same per-step cost, 61.4 against 59.0 ms at batch 32, and found its k=1 graph tripping an Inductor fusion assertion, so the log-sum-exp moved into the draft sampler).

Job 278958 (2026-11-08, a5c238c, a 250 W A40 node, so lower absolute numbers) reran the comparison with the fix and a profiled pair: the k=1 graph compiles, and within the job sampled drafts beat argmax drafts on chat at every batch size (batch 32: 974 / 970 against 898 / 934 tok/s, +4-8%; batch 8 +2%; batch 1 +2%; mixed batch 32 level; with the switch 1003 against 1001), while the T=0 control is now identical in tokens, steps and time (997.2 against 996.9). The sampled path still costs 2.0 ms more per step at batch 32 (68.5 against 66.5 ms), and the profiler shows where: the sampler kernels take 1.5 ms per step against 0.17 ms, most of it the draft sampler at 183 us per call, four calls per step, for an argmax over 32 rows of 151936 logits that should take 15 us of bandwidth. The cause is in Inductor (`torch/_inductor/ir.py`, `Reduction.num_splits`): a reduction containing an argmax is never split across thread blocks, so each row runs on one block, 32 blocks on an A40's 84 SMs, and the log-sum-exp and noise fused into the same kernel run on those 32 blocks too. The samplers now reduce each row in 128 chunks (`chunked_argmax` / `chunked_logsumexp`: max and index per chunk, then over the chunks; identical results, ties included) and draw their noise with `torch.rand` inside the kernel instead of the `exponential_` fallback that went through a 19 MB tensor; `bench_sampler.py` times the samplers on their own. Job 279567 (2026-11-09) measured that version: a single row got 31-39% faster in `Sampler` / `DraftSampler` (the one-block latency chain is gone), but at batch 32 `DraftSampler` was unchanged (220 us) and the rejection sampler slower, because the 1187-element chunks exceed Inductor's 1024-element persistent-reduction limit, so each stage became a looped reduction reading the logits twice, and the noise is still a 19 MB tensor (Inductor realizes every random tensor). The chunks are now 128 elements (1187 chunks). Job 281207 (2026-11-09) timed the three versions in one job: at batch 32 the 128-element chunks are the best torch version (`Sampler` 166 us against 196, the rejection sampler 469 / 733 against 582 / 993), but `DraftSampler`, called four times a step, stayed at 213-220 us in all three, and the per-kernel profile shows why: Inductor compiled the greedy-max + log-sum-exp stage as a looped reduction (124 us, 78 GB/s) although the chunk is 128 elements, while the Gumbel stage of the same function came out persistent (42.6 us, ~680 GB/s), with the roles reversed in `Sampler`; the choice is not controllable from the graph, and the noise is a realized 19 MB tensor in every version. End to end the sampled path cost 0.6-1.6 ms more per step at batch 32 and gave +1.8-5.6% throughput on chat (+10% at batch 8, mixed +2.9%, T=0 identical). So on the GPU `Sampler` and `DraftSampler` now run two hand-written Triton kernels (`fused_sample`): one program per (row, 1024-logit tile) reads its tile once into registers and produces the greedy max and index, the log-sum-exp as a (max, sum) pair and the Gumbel max and index with the noise generated in registers by `tl.rand`, and a second kernel combines the tiles per row (first-index ties like `torch.argmax`). Without a GPU the kernels run in Triton's interpreter for the tests (`tests/test_triton_sampler.py`) and the samplers keep their compiled torch path. Job 996212 (2026-11-09) measured them: GPU time per call at batch 32 fell from 207 / 167 us to 64 us for `DraftSampler` / `Sampler` (2 launches instead of 6; 20 us at batch 8, 7 us at batch 1, the wall time now dominated by the ~60 us of launch overhead that the engine hides behind the GPU), the rejection sampler is unchanged, `TORCHINDUCTOR_COOPERATIVE_REDUCTIONS=1` changed nothing for the torch version, and end to end the sampled path costs 0.6-0.7 ms more per step at batch 32 (was 0.6-1.6), which is now exactly four draft-sampler calls plus the rejection sampler's sampled branch (728 against 467 us). Throughput sampled against argmax drafts: chat batch 32 +4-5%, batch 8 +4%, batch 1 +5%, mixed +1%, T=0 identical tokens. The tile kernel ran at 160 GB/s, instruction-bound, half of it the Philox generator (`tl.rand` keeps one of the four numbers a Philox call produces), so it now draws four uniforms per call with `tl.rand4x`; job 1275031 (2026-11-09) measured it: the tile kernel 60.5 -> 45.0 us at batch 32 (49 us of GPU time per call), both GPU paths within 1e-7 relative of a float64 log-sum-exp (`bench_sampler.py --check`; the failed test was Inductor's compiled log-sum-exp overflowing on T=0 rows, which no log-norm reader ever sees, and the test now excludes them for the torch path), and the sampled path 0.4-0.8 ms per step above argmax drafts at batch 32, 1% of a step, with chat throughput +5-6% at batch 32, +3% at batch 1, mixed +8%, T=0 identical. That closes this line: what remains is accounted for item by item (four draft-sampler calls, the rejection sampler's sampled branch, the draft logits' traffic) and a Triton rejection sampler would save at most 0.3 ms more.

**Per-sequence k (2026-10-29, CPU phase).** `speculative_per_sequence=True` moves the acceptance rates and the probe counter from the batch to each sequence, so the edit half of a mixed batch keeps k=4 while the chat half runs at 0 (n-gram) or 2-3 (draft model), in the same step. The step's inputs become one row per token with a layout tensor (`ModelRunner.ragged_layout`) saying which rows belong to which sequence; such a step runs eagerly through `flash_attn_varlen_func` over the block tables, the same path chunked prefill uses, and the rejection sampler gathers each sequence's rows by the layout and masks the draft positions it does not have. The draft model skips the sequences without drafts (their draft cache falls behind, as in a step without drafts) and scores a dummy row for the sequences with fewer drafts than the step's maximum. Steps where every sequence has the same k, including none, are unchanged: fixed-width kernel, CUDA graphs. Verified on CPU: 9 scheduler tests, 5 sampler tests (a ragged batch gives every sequence exactly what the uniform batch of its own k gives, and sampled rows follow the target distribution), five simulator modes that check every ragged step's layout, catch-up and dummy rows against an independent computation, and a mutation table in the design note. The first A40 job (233573; raw rows in `docs/benchmarks/qwen3-8b-a40-perseq.txt`) found the draft model's ragged path crashing on an int64 context length (fixed, with a dtype check in the simulator), per-sequence probes falling on different steps and turning 21% of chat steps into eager ragged steps (the probes are now the batch's, one uniform step), and the eager ragged steps costing more than they gain at batch 8 (draft switch on the mixed batch: 1.27x per sequence against 1.43x batch-wide, with 80% ragged steps; the CUDA graphs are worth 4% at batch 32). So a second way to run a ragged step was added, `speculative_ragged="pad"`: every sequence gets `1 + max k` rows, its own right-aligned behind dummy rows (slot masked, position 0), the trick the draft model's catch-up step already uses; the fixed-width kernel's bottom-right causal alignment gives each real row exactly its keys, so the step keeps the kernel, the CUDA graphs and the sampler, and only pays for the dummy rows (cheap at batch 8, not at batch 32, where `varlen` computes 96 rows eagerly instead of 160 through a graph). The second and third A40 jobs (233732, 234187) settle it: `pad` beats `varlen` by 17-19% at batch 8 and by 5-12% on chat at batch 32, and loses 2-3% on the mixed batch at 32 (160 rows against 96), so `pad` is the default. But per-sequence k itself beats the batch-wide switch nowhere on this A40 with Qwen3-8B + 0.6B: mixed batch 8 1.24x against 1.38x, batch 32 1.02x against 1.12x, chat batch 32 1.02x. The acceptance rate rises as designed (0.57 to 0.63) and the outputs match the reference, but `varlen` gives up the CUDA graphs (worth 25% at batch 8) and `pad` computes the same rows and draft-model steps as a uniform batch at the largest k, so it can only accept fewer tokens. The ceiling was small to begin with: at batch 32, fixed k=4 (1.14x) and the batch-wide switch (1.12x) are two points apart, which is all the chat half's wasted positions cost while decode is still bound by weight reads. The mode stays, off by default, with the numbers and the two things a win would need (ragged attention under CUDA graphs, a draft model that only works for the sequences that draft) in the design note.

What the numbers say:

- A 0.6B drafter speeds up the 8B model on every workload and batch tested: 2.9x on code editing and 1.8x on chat at batch 1, still 1.45x and 1.16x at batch 32. Sampling at T=0.6 costs nothing over greedy, so the rejection sampler is doing its job.
- N-gram drafts are the honest worst case: 2.8x on code editing, where the output copies the input (acceptance 0.5), but useless on chat (acceptance 0.05), where they slow decoding down at batch 8 and 32; the acceptance switch turns them off there and brings chat back to within 1% of the baseline (job 232099).
- Async scheduling gave +10% on Qwen3-0.6B and nothing measurable on Qwen3-8B: the CPU work it hides is a fixed few milliseconds per step, large next to a 0.6B forward pass and small next to an 8B one.
- Adaptive speculation behaves as designed below its threshold (same numbers as draft k=4) and now costs nothing above it: 0.98x on edit and 1.00x on chat at batch 32, where it switches drafts off (0.96x and 1.01x with async scheduling on top). Its first version measured 0.76x and 0.85x there, because the draft model still ran one step per decode step to keep its KV cache current, and that step reads the draft's whole KV cache, which for Qwen3-0.6B is 28 layers of the same per-layer size as the 8B's 36. The fix lets the draft cache lag while drafts are off and catches it up in one forward pass when they resume (the design note has the mutation table).
- The threshold is the remaining lesson: on this A40 the 8B target is still memory-bound at batch 32, so leaving draft k=4 on (1.45x on edit, 1.10x on chat) beats switching it off at 8 sequences. The threshold belongs where the target turns compute-bound, and the better switch is measured acceptance: it would turn n-gram drafts off on chat (acceptance 0.05) and leave model drafts (0.40 to 0.85) on. `speculative_min_acceptance` is that switch, extended to pick `k` per step from each draft position's acceptance rate (position `j` is only accepted when the `j-1` before it were, so the rates fall with the position and the cut lands where they drop below the threshold); the tables above show one setting giving 3.2x on edit at batch 1 and 1.19x on chat at batch 32, where fixed k=4 gets 1.04x and fixed k=6 loses.
